## 2. Technical Course-Corrections & Key Decisions

The final review found four issues that would have affected a reviewer's first run or the contract match. Each was fixed and re-verified.

### A. Testcontainers Version Pinning (Docker Engine 29 Compatibility)
* **The Issue:** Spring Boot 3.5.6 manages Testcontainers at version `1.21.3`. Its default Docker API version is below the minimum accepted by Docker Engine 29.x, so the engine rejected the connection with `Status 400` and every test failed before running.
* **The Refinement:** Pinned Testcontainers to `1.21.4` in `build.gradle.kts` (`extra["testcontainers.version"] = "1.21.4"`), which negotiates a supported API version. `./gradlew test` now runs against a real `postgres:15-alpine` container on Docker Engine 29.

### B. OpenAPI Contract Realignment (GET Validation Removed)
* **The Issue:** A blank or 65+ character SKU passed to `GET /inventory/{skuId}` returned `400 Bad Request` because of path-variable validation constraints. The contract permits only `200 OK` or `404 Not Found` for this operation.
* **The Refinement:** Removed the `@NotBlank` / `@Size` constraints from the `GET` path variable only. Such a SKU can never exist in the table (the column is `VARCHAR(64)` with a non-blank CHECK constraint), so the normal repository lookup finds no row and the service's existing `SkuNotFoundException` path returns `404`. No special-case code was added. The `POST` routes keep the constraints, because the contract allows `400` there and an invalid SKU must never be created. A new integration test, `get returns 404 rather than 400 for a SKU id too long to exist`, covers the change.

### C. Eliminating Onboarding Friction
* **The Issue:** `.env.example` shipped with empty credentials, so following the README literally (`cp .env.example .env`, then `docker compose up -d`) failed with `required variable POSTGRES_USER is missing a value`.
* **The Refinement:** `.env.example` now ships throwaway local-only values (`POSTGRES_USER=inventory`, `POSTGRES_PASSWORD=inventory_local_dev`). A reviewer can now run `cp .env.example .env && docker compose up -d` without editing anything. The real `.env` remains git-ignored, and `application.yml` still has no credential defaults, so deployed environments must supply their own.

### D. README Troubleshooting
* **The Issue:** Environment problems met during development were undocumented:
  * A Homebrew PostgreSQL on port 5432 intercepted the app's connection.
  * The `docker` CLI was missing from `PATH`.
  * Gradle cannot run on Java 27.
  * `bootRun` appears stuck at `85% EXECUTING` while the server runs.
* **The Refinement:** Added a Troubleshooting section to `README.md` with the diagnostic command and fix for each.

## 3. Defensible Talking Points

The following design choices are the ones most worth discussing in the follow-up conversation:

* **No JVM lock state:** Concurrency protection relies on PostgreSQL rather than in-memory locks. Purchases take a row lock (Hibernate renders `PESSIMISTIC_WRITE` as `SELECT … FOR NO KEY UPDATE`), restocks use an atomic `INSERT … ON CONFLICT DO UPDATE`, and a CHECK constraint keeps stock non-negative. The service therefore scales horizontally with no coordination between replicas. The practical limits are documented in `tech-spec.md` §4.8 and §8:
  * Throughput on a single hot SKU is bounded by row-lock hold time.
  * Replica count is bounded by `connection pool size × replicas < PostgreSQL max_connections`.
* **HOT update optimization:** Every purchase or restock writes a new row version under MVCC. `fillfactor = 90` leaves 10% free space on each heap page, so PostgreSQL can usually place the new version on the same page as a heap-only tuple (HOT) update. Because `quantity` is not indexed, the primary-key index is then not touched, reducing index churn and vacuum work.
* **Fail-fast boundaries:** Hibernate runs with `ddl-auto: validate`, so Flyway owns the schema and any entity/schema mismatch stops startup. Strict Jackson settings (`accept-float-as-int: false`, `allow-coercion-of-scalars: false`) reject `2.7` and `"5"` at deserialization instead of silently truncating or coercing them.
